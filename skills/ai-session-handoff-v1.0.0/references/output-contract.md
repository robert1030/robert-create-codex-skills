# 交接文件輸出契約（v1.0.0 凍結）

九節標題的文字與順序為凍結契約，照抄不改字、不刪節。權威來源是 `scripts/handoff_contract.py` 的 `HEADINGS`，`scripts/validate_skill.py` 會比對本檔、SKILL.md 與 schema 三處是否一致。

## 通用規則

- **不適用的節**：寫「本節無內容。」保留節標題，不得省略。
- **事實分級標記**：`[CONFIRMED]`、`[INFERRED]`、`[UNVERIFIED]`、`[BLOCKED]`、`[SUPERSEDED]`，五選一。決議、artifact、風險等敘述逐條標示。判定準則：使用者親口說或工具結果證實的是 `[CONFIRMED]`；由證據推出但沒人確認過的是 `[INFERRED]`；還沒查證的是 `[UNVERIFIED]`；因缺權限、缺檔案、缺工具或等使用者拍板而卡住的是 `[BLOCKED]`；被後續決議推翻但值得留著避免重蹈的是 `[SUPERSEDED]`。
- **遮蔽標記**：秘密值一律換成 `[REDACTED]`，保留用途與存在位置。
- **artifact 紀律**：引用而非複製。每筆寫「路徑或 URL ＋ 一句用途 ＋ 目前狀態 ＋ 下一個 agent 該讀哪一段」，並帶狀態標記。檔案不存在或無法存取時標 `[BLOCKED]` 或 `[UNVERIFIED]`，不得靜默略過，更不得虛構。
- **標題行**：文件第一行寫 `# Session 交接摘要｜〈主題〉｜〈日期〉`，其中角括號換成真內容（角括號留著會被驗證器當成佔位符）。
- **章節層級**：九節一律用 `##`。
- **長度**：以「下一個 agent 能否據以行動」為準。單節長到讀者需要先摘要一次才能用，就代表該再濃縮。
- **交付形式**：web 模式放進單一可整塊複製的 fenced code block，語言標記用 `markdown`；文件內部含三反引號時，外層改用四個反引號以免巢狀斷裂。agent 模式寫入暫存目錄並回讀驗證後回報完整路徑。
- **涵蓋誠實聲明**：`scripts/validate_handoff.py` 驗得了結構、標記合法性、必填欄位與明文秘密，驗不了內容是否忠於對話。「祈使語氣」無法可靠機器判定，屬人工留意項，不在閘門內。

## 〇、啟動指令（給下一個 session）

**目的**：讓接手的 agent 讀完這一節就知道第一個動作是什麼。

**三條機器閘門**：內文去除空白後不超過 200 字；至少三個編號條目（圓圈數字或行首阿拉伯數字皆可）；第一個編號條目必須同時含「讀」與「再回應」，以防搶答飄移。開場定位句屬合法前導，契約錨定在第一個編號條目。

**必含**：先完整讀本文件再回應、要載入哪些 skill 與紀律、從第一節的下一步接手、哪些內容不可重新決策、動工前要驗證哪些條件。

**寫法**：

```text
你是接手本工作的新 session。請依序執行：①完整讀完本文件再回應；②載入第四節列出的 skill 與紀律；③嚴守第五、第六節，凍結項不重新決策；④從第一節的下一步接手，動工前先複述你的理解與待驗證條件。
```

## 一、任務身分卡

**目的**：十秒定位。先給答案，再給細節。

**必含欄位**：任務名稱；任務目標；使用者期望與驗收標準；目前階段；主要交付物；完成標準；下一步（接手後第一件事）；下一個 session 的指定焦點（使用者沒指定就寫「通用延續」）。

**排除**：過程敘事、心得、與驗收無關的背景。

## 二、核心脈絡

**目的**：只放「不知道就會誤解後文」的背景。

**必含**：問題起點與為什麼要做；關鍵名詞、代號、縮寫的定義；影響後續推理的環境條件（作業系統、語言、平台、既有系統）。

**排除**：社交寒暄；無關支線；已被後續決策取代的暫時想法（要留就進第七節並標 `[SUPERSEDED]`）；不影響後續工作的重複說明。

## 三、工作流現況

**目的**：讓接手者分得清做完的與只討論過的。

**必含六種狀態**：已完成、進行中、尚未開始、被阻塞、已放棄、需要驗證。每條附 artifact 引用（路徑、URL、commit、產出物名稱、版本號）與狀態標記。

**硬規則**：「曾討論」不得寫成「已完成」；未執行的測試不得寫成已通過；未建立的檔案不得寫成已存檔。

**寫法**：

```text
- 已完成：結構驗證器 `scripts/validate_handoff.py`｜九節與紀律閘門｜本機實測退出碼 0 [CONFIRMED]
- 被阻塞：部署腳本 `deploy/release.sh`｜等待雲端權限｜檔案存在但無法執行 [BLOCKED]
```

## 四、工作紀律與規範

**目的**：讓接手者用同一套規矩繼續工作。

**必含**：語言與用詞；格式與標點；編碼要求；平台限制；品管與驗證程序；研究與引用要求；建議載入的 skill 或工具（寫名稱讓對方自行載入，不要整段抄進來）。

**排除**：把整支 skill 的內文複製進來。

## 五、邊界與禁區

**目的**：說清楚哪些事不做、界線在哪。

**寫法**：以正向目標行為為主，例如「檔案一律寫入暫存目錄」而不是「不要寫進專案目錄」。只有涉及安全、資料破壞、敏感資訊、不可逆操作或凍結契約時保留硬性禁止，並同時寫出正確的替代行為與理由。

## 六、凍結契約與關鍵閘門

**目的**：標出不可重新決策的區域。

**必含**：不得改動的輸出結構；已接受的 schema；已確認的名稱與版本；必須通過的 validator；不可跳過的測試；需先滿足的前置條件；每項附定版時點。

**寫法**：`- 九節骨架標題與順序（2026-08-04 定版）｜改動一律另開 major 版本 [CONFIRMED]`

## 七、已確認的對話決議

**目的**：把「誰決定的、為什麼、還能不能改」講清楚。

**每條必含**：決議內容；決議原因；影響範圍；是否可重新討論；相關 artifact 或來源；狀態標記。頂層條列缺標記會被驗證器擋下。

**硬規則**：AI 建議而使用者只是沒反對的，標 `[INFERRED]` 或 `[UNVERIFIED]`，不得標 `[CONFIRMED]`。

## 八、未決事項與風險

**目的**：把地雷先講出來。

**必含分類**：已知未知；待使用者決定；待外部查證；技術風險；平台差異；缺少檔案或權限；可能造成資料遺失的事項。

**必填欄位**：`脈絡涵蓋`。寫本次實際看得到的對話範圍與來源時間，例如「脈絡涵蓋：本對話全程可見，最後更新 2026-08-04」或「脈絡涵蓋：早段已被壓縮，僅能交接可見部分，建議向使用者確認起始需求」。缺這一欄驗證器會擋下。
