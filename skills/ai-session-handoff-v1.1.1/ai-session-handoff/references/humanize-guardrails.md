# 人話化保護清單（Step 5.5 專用，v1.0）

本檔定義 Step 5.5（人話化）的保護範圍：哪些內容絕對不可被改寫、哪些內容可以自由潤飾。權威來源是 `scripts/handoff_contract.py` 的凍結常數；本檔內容一旦與該檔漂移，以程式常數為準。

---

## 第一層：絕對唯讀，不得列入人話化候選清單

以下九項由 `scripts/humanize_filter.py` 在候選清單生成前自動剔除，使用者不會看到、也不需要手動勾除。

| # | 保護對象 | 對應常數 | 為什麼絕對不可動 |
| --- | --- | --- | --- |
| 1 | 九節標題文字＋順序 | `HEADINGS` | `assert_frozen()` 以 sha256 比對章節清單，動一字即整包判定凍結契約被破壞 |
| 2 | 狀態標記字面 | `STATUS_TAGS`、`ALLOWED_BRACKET_TOKENS` | `validate_handoff.py` 檢查非法方括號標記，改寫成同義詞會被判定為未知標記 |
| 3 | 「本節無內容。」固定句 | `EMPTY_SECTION_TEXT` | 空節判定用逐字比對，換句話說會被誤判為空節 |
| 4 | 「脈絡涵蓋」四字 | `COVERAGE_MARKER` | 第八節必填欄位用字串比對確認存在，改寫會被判定為缺欄位 |
| 5 | 第〇節錨詞「讀」＋「再回應」 | `BOOT_ANCHORS` | 第一個編號條目須同時含這兩個字，是機器判定「第一動作」的依據 |
| 6 | 第〇節編號條目數量與字數上限 | `BOOT_MIN_ITEMS`、`BOOT_MAX_CHARS` | 去編號或拉長敘述會直接違反這兩條上限／下限 |
| 7 | 第七節每條決議的狀態標記 | `STATUS_TAGS`（配合 `DECISION_SECTION_INDEX`） | 防止把「AI 建議但未確認」的推論改寫成看起來像已拍板的事實 |
| 8 | 第三節 artifact 引用行的狀態標記 | `STATUS_TAGS`（配合 `ARTIFACT_SECTION_INDEXES`） | 防止虛構或未驗證的檔案宣稱在潤稿過程中被連標記一起抹掉 |
| 9 | `[REDACTED]` 不可被改寫成委婉同義詞 | `REDACTION_MARK` | 改寫成「已隱藏」「已省略」等說法會被判定為非法標記，也會讓遮蔽狀態變得不可追蹤 |

## 第二層：可以潤飾語氣，但不能刪內容、不能動結構

| 節 | 可動範圍 | 不可動範圍 |
| --- | --- | --- |
| 一、任務身分卡 | 敘述句用詞、贅字 | 必含欄位本身不可減項（任務目標、驗收標準、下一步等） |
| 二、核心脈絡 | 背景說明語感 | 關鍵名詞定義不可被誤判為套話而刪除 |
| 三、工作流現況 | artifact 用途的敘述措辭 | 六種狀態分類與狀態標記（見第一層 #8） |
| 四、工作紀律與規範 | 說明文字 | skill 名稱＋檔名的固定寫法（下一個 agent 靠這個解析路徑） |
| 五、邊界與禁區 | 敘述語氣 | 涉及安全、資料破壞、不可逆操作的硬性禁止語句不可弱化成建議語氣 |
| 六、凍結契約與關鍵閘門 | 幾乎不動，本質是條列事實 | 定版時點格式、驗證器名稱 |
| 七、已確認的對話決議 | 決議原因、影響範圍的敘述 | 狀態標記（見第一層 #7）；見下方「語意強度保護」 |
| 八、未決事項與風險 | 分類項敘述 | 「脈絡涵蓋」欄位（見第一層 #4） |

## 語意強度保護（pre-mortem 防範條款一）

**規則**：緊鄰狀態標記的敘述句，人話化只能換句法與贅字，不能換語意強度。

背景：曾出現過一種失敗模式，標記本身沒被砍（機器驗證仍綠燈），但標記旁邊用來佐證「這只是推論、不是拍板事實」的限定語（例如「建議但未經確認」「尚待查證」）在人話化過程中被當成 speak-human-tw 規則裡的「立場真空／模糊歸屬」套話砍掉或稀釋，導致下一個 AI 讀到改寫後的敘述時，讀不出原本的不確定程度，逕自把 `[INFERRED]` 當成 `[CONFIRMED]` 執行。

**具體要求**：改寫第六、七節裡緊鄰狀態標記的句子時：

- 可以：換掉生硬的詞、砍掉真正的贅字、調整語序。
- 不可以：把「這是建議、尚未確認」這類限定語整句刪除或改寫成聽起來已經拍板的語氣。
- 判斷方式：改寫前後，讀者單看敘述文字（不看標記）能不能得出同等的確定程度；得不出來就是稀釋了語意強度，這條候選項不該被使用者勾選套用。

此規則無法完全靠 `humanize_filter.py` 的字串比對機械判定（語意強度是連續量，不是字串存在與否），因此在 Step 5.5 流程另有一道人工抽查關卡（見 SKILL.md「Step 5.5」的套用後語意強度抽查）。

---

## 使用方式

1. 產出人話化候選清單前，先跑 `scripts/humanize_filter.py <candidates.json>`，取得已剔除第一層九項的 `kept` 清單。
2. 只把 `kept` 清單交給使用者做雙重確認（先列清單、等勾選）。
3. 套用完成後，凡命中第六、七節的項目，額外附加一行語意強度抽查提示（見上方「語意強度保護」）。
4. 套用完成後重跑 `scripts/validate_handoff.py`，非 0 不得交付。
