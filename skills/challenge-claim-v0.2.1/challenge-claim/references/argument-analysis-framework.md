# 論證分析框架

本文件定義 `challenge-claim` 分析主張、理由、證據、前提、推理鏈、反例與結論信心的共同格式。它用於將一段自然語言重建成可檢查的論證，辨識缺漏與不當推論，再提出有根據的挑戰與修正版結論。

本框架強調「協助思考」而非直接替使用者下判斷。分析者應先釐清論證，再檢查證據與推理，最後說明哪些部分已獲支持、哪些部分仍需查證。

---

## 1. 適用範圍

適合分析：

- 文章、報告、新聞、研究摘要或社群貼文中的核心主張。
- 政策建議、商業決策、產品比較或風險判斷。
- 使用者自己的推理、簡報論點或決策依據。
- 包含明示理由，也包含需要由語境重建的隱含前提。
- 需要辨認反例、替代解釋或證據不足的結論。

不適合直接取代：

- 需要專業資格才能完成的法律、醫療或投資決策。
- 未提供原文、資料或可辨識主張的純粹情緒表達。
- 只要求摘要、翻譯、改寫或文法校訂，而未要求檢查論證。
- 單純產生支持某立場的宣傳文案。

若使用者只提供模糊主題，先詢問要分析的具體主張、文本範圍與決策目的。

---

## 2. 核心原則

### 2.1 先重建，再批判

先忠實表述對方想主張的內容，再指出問題。不要一開始就以結論、立場或價值判斷取代分析。

### 2.2 分離主張、證據與推論

「有人這樣說」是來源描述，不等於證據；「資料相關」也不自動等於「前者造成後者」。每個元素都要分開標示。

### 2.3 明示不確定性

使用「目前資料支持」「尚不足以支持」「若前提成立則」「此處需要補充證據」等可校準語句，避免把分析信心寫成二元斷言。

### 2.4 主動尋找可反駁條件

好的挑戰不是單純提出相反意見，而是說明：

- 哪個觀察會削弱原結論。
- 哪個替代解釋能同樣說明資料。
- 哪個邊界條件會使推論失效。
- 需要什麼新證據才能提高或降低信心。

### 2.5 對人保持中立，對推理保持嚴格

批判對象是主張、證據與推理鏈，不是作者的智力、動機或人格。除非使用者提供可驗證資料，否則不推測惡意、偏見或欺騙意圖。

## 3. 分析對象的標準結構

每份分析至少建立下列結構：

```text
主張 Claim
├── 理由 Reason
│   ├── 證據 Evidence
│   └── 前提 Premise
├── 推理鏈 Inference
├── 反例 Counterexample
├── 替代解釋 Alternative explanation
└── 結論信心 Confidence
```

### 3.1 主張 Claim

主張是作者希望讀者接受的命題、判斷或行動建議。

應記錄：

| 欄位 | 說明 |
|---|---|
| `claim_id` | 唯一識別碼，例如 `C1` |
| `text` | 以一句話寫出主張 |
| `type` | 事實、因果、預測、價值判斷或規範建議 |
| `scope` | 適用對象、時間、地點與條件 |
| `strength` | 原文主張的強度，例如「可能」「通常」「必然」 |
| `importance` | 對整體結論的重要程度 |

主張應盡量具體：

```text
不佳：這個政策不好。

較佳：在目前預算與執行人力不變的情況下，該政策可能無法在下一年度達成既定的服務覆蓋率。
```

### 3.2 理由 Reason

理由是作者用來支持主張的命題。理由本身也可能需要分析。

```text
R1：該政策需要大量新增人力。
R2：目前編列預算未包含相應的人事成本。
R3：過去相似計畫曾出現執行延遲。
```

一個理由若只是重述主張，不能視為獨立支持。

```text
主張：這項方案不可行。
理由：因為它是不可行的。
問題：理由沒有提供額外資訊，屬於循環論證。
```

### 3.3 證據 Evidence

證據是支持或削弱理由、前提或主張的可檢查資料。可包含：

- 原始數據。
- 實驗結果。
- 研究或官方文件。
- 可重現的觀察。
- 具體案例。
- 專家判斷。
- 使用者提供的第一手經驗。

每項證據記錄：

| 欄位 | 說明 |
|---|---|
| `evidence_id` | 唯一識別碼，例如 `E1` |
| `source` | 來源或提供者 |
| `observation` | 證據實際顯示什麼 |
| `supports` | 支持哪個理由或主張 |
| `quality` | 來源可靠性、樣本、方法與時效 |
| `limitation` | 證據不能證明什麼 |
| `status` | 已確認、待查證、相互矛盾或不可用 |

範例：

```text
E1
來源：試辦計畫月報
觀察：三個試辦地區的平均處理時間增加 18%。
支持：R3「新增流程可能造成執行延遲」。
限制：樣本只有三個地區，且試辦期間缺乏長期追蹤。
狀態：已提供，但外推性有限。
```

### 3.4 顯性前提 Explicit Premise

顯性前提是文本直接說出的假設或條件。

```text
P1：若新增服務需要每案增加兩小時人力，則現有人力不足以維持原服務量。
P2：該機構下一年度不會大幅增加預算。
```

顯性前提仍需檢查真實性，不因作者明確寫出就視為成立。

### 3.5 隱含前提 Implicit Premise

隱含前提是推理成立所需、但文本未直接說出的條件。重建隱含前提時，應採取「最小合理補充」：

- 只補上推論所必要的條件。
- 不替作者加入更強或更極端的主張。
- 清楚標記這是分析者重建，而非原文直接陳述。
- 若存在多種合理前提，列出主要版本。

範例：

```text
原文：其他城市用了這套系統後效率提升，因此本市也應立即導入。

可能的隱含前提：
IP1：其他城市與本市在需求、資源、法規與執行能力上足夠相似。
IP2：效率提升主要由該系統造成，而非同時進行的流程改革。
IP3：本市立即導入的成本與風險低於延後試辦的成本。
```

### 3.6 推理鏈 Inference Chain

推理鏈說明理由如何支持主張。可用編號箭頭表示：

```text
E1：試辦地區處理時間增加 18%
→ R1：新增流程可能增加工作量
→ IP1：本機構的人力與案件結構與試辦地區相近
→ C1：全面導入可能造成服務延遲
```

每條推理鏈檢查：

1. 證據是否真的支持前一層理由。
2. 理由是否足以推出下一層結論。
3. 是否從可能跳到必然。
4. 是否遺漏重要中介條件。
5. 是否將相關性誤當因果性。
6. 是否將少數案例外推至整體。
7. 是否將價值偏好偽裝成事實結論。

## 4. 主張類型與專用檢查

### 4.1 事實主張

例：

> 這項措施使平均處理時間下降 20%。

檢查：

- 指標如何定義？
- 比較基準是什麼？
- 資料期間與樣本為何？
- 是否存在選樣、測量或報告偏差？
- 結果是否能被獨立重現？

### 4.2 因果主張

例：

> 導入系統後效率提高，因此系統造成效率提高。

檢查：

- 是否有時間先後？
- 是否有對照組或替代基準？
- 是否有其他同時發生的變因？
- 是否可能是反向因果？
- 因果機制是否具體？
- 是否存在外推限制？

建議將「觀察到」與「造成」分開：

```text
觀察：導入後效率提高。
尚未證明：效率提高完全由導入系統造成。
可能替代解釋：同期增加人力、改變流程或案件難度下降。
```

### 4.3 預測主張

例：

> 這項投資三年內一定會回本。

檢查：

- 預測期間是否明確？
- 關鍵變數與假設是否列出？
- 是否提供基準情境、樂觀情境與悲觀情境？
- 「一定」是否超過證據可支持的強度？
- 失敗條件與提前警示指標是什麼？

### 4.4 價值判斷

例：

> 這項政策是不公平的。

檢查：

- 公平採用什麼標準？
- 評估對象是結果、機會、程序還是負擔分配？
- 不同價值標準會否得出不同結論？
- 是否把個人偏好描述成客觀事實？

### 4.5 規範或行動建議

例：

> 因此政府應立即禁止該產品。

檢查：

- 問題嚴重性是否足以支持該行動強度？
- 是否比較過較低成本或較低限制的替代措施？
- 行動的副作用與執行可行性為何？
- 是否有明確的適用條件、期限與檢討點？

## 5. 論證重建格式

### 5.1 最小重建表

```markdown
## 論證重建

| ID | 類型 | 內容 | 來源／狀態 |
|---|---|---|---|
| C1 | 主張 | 全面導入方案可能造成服務延遲。 | 原文明示 |
| R1 | 理由 | 試辦期間平均處理時間增加。 | 原文明示 |
| E1 | 證據 | 三地區平均處理時間增加 18%。 | 使用者提供資料 |
| IP1 | 隱含前提 | 本機構與試辦地區的人力和案件結構相近。 | 分析重建 |
| P1 | 顯性前提 | 預算不會同步增加。 | 原文明示 |
```

### 5.2 依賴關係表

```markdown
## 推理依賴

| 上游 | 關係 | 下游 | 檢查結果 |
|---|---|---|---|
| E1 | 支持 | R1 | 部分支持；樣本有限 |
| R1 + IP1 | 支持 | C1 | 條件式支持 |
| P1 | 強化 | C1 | 前提未驗證 |
```

### 5.3 以自然語言重述

```text
較忠實的重述是：

如果試辦地區的處理時間增加主要來自新增流程，而且本機構面臨相似的人力與案件條件，
同時預算不會同步增加，那麼全面導入可能造成服務延遲。

因此，現有資料支持「需要先進行小規模試辦與容量評估」，
但尚不足以支持「全面導入必然失敗」。
```

## 6. 挑戰論點的檢查清單

### 6.1 定義與範圍

- [ ] 主張是否能用一句話清楚表示？
- [ ] 關鍵詞是否有操作性定義？
- [ ] 適用對象、時間與條件是否明確？
- [ ] 原文是描述、因果、預測、價值判斷還是行動建議？
- [ ] 結論強度是否與原文一致？

### 6.2 證據品質

- [ ] 每個重要理由是否有對應證據？
- [ ] 來源是否可追溯？
- [ ] 證據是否直接涉及主張，而非僅涉及相鄰議題？
- [ ] 樣本是否足以支持外推？
- [ ] 資料是否過時、選擇性呈現或缺少比較基準？
- [ ] 是否存在相反證據？
- [ ] 證據能支持多強的結論？

### 6.3 前提完整性

- [ ] 顯性前提是否成立？
- [ ] 是否需要補出隱含前提？
- [ ] 隱含前提是否把多個不同條件混在一起？
- [ ] 哪個前提一旦不成立，結論就會失效？
- [ ] 是否把價值選擇誤當成事實前提？

### 6.4 推理有效性

- [ ] 是否從相關性跳到因果性？
- [ ] 是否從少數案例推廣到所有情況？
- [ ] 是否從「可能」跳到「必然」？
- [ ] 是否忽略基準率或替代解釋？
- [ ] 是否將對方立場過度簡化？
- [ ] 是否攻擊人物而非論點？
- [ ] 是否使用錯誤二分法？
- [ ] 是否把沒有證據誤當成反證？
- [ ] 是否以結論本身作為理由？
- [ ] 是否把例外情況當成普遍規則？

### 6.5 決策可用性

- [ ] 是否指出需要補充的最小資訊？
- [ ] 是否提供可執行的下一步？
- [ ] 是否說明不同前提下的不同結論？
- [ ] 是否標記不可逆或高風險行動？
- [ ] 是否區分「論點較弱」與「論點已被證偽」？

## 7. 常見問題模式

以下分類用於定位問題，不代表看到關鍵詞就直接判定錯誤。

| 模式 | 判定方式 | 修正方向 |
|---|---|---|
| 循環論證 | 理由只重述結論 | 補充獨立證據或中介理由 |
| 過度外推 | 少數樣本推出普遍結論 | 限定範圍、補樣本或改弱結論 |
| 相關不等於因果 | 同時變動被當成原因 | 說明機制、對照與替代解釋 |
| 錯誤二分 | 只列兩種選擇，忽略中間方案 | 建立選項矩陣 |
| 稻草人 | 將對方主張改成較容易攻擊的版本 | 先提供最強合理重述 |
| 人身攻擊 | 以人物特徵取代論據 | 回到命題、資料與推理 |
| 訴諸權威 | 以權威身分取代證據 | 說明權威的專業範圍與原始資料 |
| 訴諸無知 | 因尚未證明為假便視為真 | 說明目前證據狀態 |
| 斷章取義 | 脫離上下文使用語句 | 還原完整脈絡 |
| 移動標準 | 反例出現後任意增加新要求 | 事先固定判定標準 |
| 過度確定 | 使用「必然」「完全」「所有」但證據有限 | 改為條件式或機率式表述 |
| 忽略成本 | 只說明好處，不計代價 | 補上成本、風險與機會成本 |
| 忽略反事實 | 未說明沒有該措施時會怎樣 | 建立基準情境 |
| 缺失前提 | 中間推論需要但未說明的條件 | 列出並逐一驗證 |

## 8. 反例與替代解釋

### 8.1 反例類型

反例不只是一個相反案例，可分為：

1. **直接反例**：符合原主張適用條件，但結果與主張相反。
2. **邊界反例**：顯示主張只在某些條件下成立。
3. **反事實反例**：若沒有被宣稱的原因，結果仍可能出現。
4. **機制反例**：結果存在，但由另一個更合理機制造成。
5. **定義反例**：主張中的關鍵詞在不同定義下得到不同結果。
6. **時間反例**：短期成立但長期不成立，或反之。

### 8.2 反例記錄格式

```markdown
## 反例

| ID | 類型 | 內容 | 影響 |
|---|---|---|---|
| X1 | 邊界反例 | 試辦地區人力充足時，新增流程未造成延遲。 | 削弱「導入必然造成延遲」，支持條件式結論 |
| X2 | 替代機制 | 延遲可能由同期訓練期造成，而非系統本身。 | 削弱因果推論 |
```

### 8.3 替代解釋模板

```text
原解釋：
A 導致 B。

替代解釋：
C 與 A 同時發生，C 也可能導致 B。

需要區分的證據：
- A 發生但 C 未發生的案例。
- C 發生但 A 未發生的案例。
- 控制 C 後 A 與 B 的關係。
- 能直接驗證 A 至 B 機制的觀察。
```

## 9. 結論信心評估

結論信心描述「目前證據對結論的支持程度」，不描述作者是否自信。

### 9.1 信心等級

| 等級 | 定義 | 建議語句 |
|---|---|---|
| 高 | 關鍵證據直接、可靠且替代解釋有限 | 「現有證據高度支持」 |
| 中高 | 主要推理成立，但仍有可處理限制 | 「大致支持，仍需確認」 |
| 中 | 證據與推理各有支持與缺口 | 「可作暫時判斷」 |
| 中低 | 依賴未驗證前提或外推 | 「僅有條件式支持」 |
| 低 | 關鍵證據缺失、矛盾或推理斷裂 | 「目前不足以支持」 |
| 不可評估 | 主張不清或沒有可檢查資料 | 「需先補充資訊」 |

### 9.2 信心報告格式

```markdown
## 結論信心

- **判定：中低**
- **目前支持：** 試辦資料顯示處理時間上升，足以支持「導入可能增加工作量」。
- **主要缺口：** 尚未確認本機構與試辦地區的人力、案件結構及訓練條件相似。
- **最大脆弱前提：** 預算與人力不會在導入時同步增加。
- **可提高信心的證據：** 本機構小規模試辦、分組比較、處理時間基準線與完整成本估算。
- **暫時結論：** 宜先試辦與容量評估，不宜直接宣稱全面導入必然失敗。
```

本節為內部分析工作表，不是交付格式。交付一律依 SKILL.md 的輸出契約七元件，兩者衝突時以 SKILL.md 為準。工作表依下列順序整理：

```markdown
# 論點挑戰分析

## 1. 分析範圍

- 使用者目的：
- 未納入範圍：
- 資料限制：

## 2. 最強合理重述
> 用不超過三句話忠實重述原論點。

## 3. 核心主張
| ID | 主張 | 類型 | 範圍 | 原文強度 |
|---|---|---|---|---|

## 4. 理由與證據
| 理由 ID | 理由 | 證據 ID | 證據摘要 | 支持程度 |
|---|---|---|---|---|

| ID | 前提 | 類型 | 是否已驗證 | 重要性 |
|---|---|---|---|---|

## 12. 實例：政策論點

### 使用者論點

> 某城市導入智慧交通系統後，平均車速提高了 15%，所以本市只要導入同樣系統，就能解決尖峰塞車問題，政府應該立即全面採購。

### 分析

```markdown
## 最強合理重述

該系統在另一城市的特定條件下與平均車速提升同時出現，
因此若兩地交通結構與執行條件相近，本市導入可能改善部分尖峰壅塞。
論點進一步主張應立即全面採購，但這個行動建議還需要成本、成效與風險證據。

## 核心主張

| ID | 主張 | 類型 |
|---|---|---|
| C1 | 導入系統可解決本市尖峰塞車問題。 | 因果／預測 |
| C2 | 政府應立即全面採購。 | 規範建議 |

## 理由與證據

| ID | 內容 | 評估 |
|---|---|---|
| R1 | 另一城市導入後平均車速提高 15%。 | 可支持「該城市的車速曾提高」，不單獨證明因果 |
| R2 | 本市與另一城市可採用相同做法。 | 需要補充兩地相似性與執行可行性 |

## 關鍵隱含前提

1. 車速提高主要由智慧交通系統造成。
2. 另一城市與本市有相似的道路結構、公共運輸、車流與執法條件。
3. 平均車速提高代表尖峰塞車問題獲得實質改善。
4. 全面採購比先試辦更能控制成本與風險。
5. 沒有其他成本、隱私或維護風險會抵銷效益。

## 主要挑戰

- 平均車速不是唯一指標；需要查看尖峰時段、不同路段、事故率與旅行時間可靠度。
- 可能存在同期道路工程、號誌調整或車流下降等替代解釋。
- 單一城市案例不足以支持本市必然得到相同結果。
- 「可能改善」不能直接推出「解決問題」。
- 成效證據不足以單獨支持「立即全面採購」。

## 反例與替代解釋

- 若另一城市同期進行道路拓寬，系統不一定是主要原因。
- 若本市瓶頸來自停車、公共運輸接駁或道路容量，號誌系統可能無法處理核心問題。
- 若試辦區域有效但其他區域無效，全面部署可能降低投資報酬。

## 修正版結論

現有資料最多支持：該系統在另一城市的特定情境下可能改善交通效率。
要支持本市採購，應先完成本市基準線、相似性分析、成本效益估算與小規模試辦。
目前不宜由單一案例推出「必然解決尖峰塞車」或「應立即全面採購」。
```

## 13. 實例：研究結果論點

### 使用者論點

> 研究發現使用 Socratic chatbot 的學生在批判思考測驗上表現較好，因此 Socratic chatbot 一定能提升所有學生的批判思考能力。

### 分析重點

1. **觀察結果**：研究組在特定測驗或研究設計中表現較好。
2. **因果推論**：是否為 chatbot 造成，需要查看研究是否有對照組、隨機分派與控制變項。
3. **外推問題**：研究對象、年齡、課程、使用時間與測驗型態可能限制普遍性。
4. **概念問題**：一次測驗分數提高，不必然等於長期批判思考能力提升。
5. **強度問題**：「所有學生」「一定」通常超過研究設計可支持的結論。

校準後結論：

> 研究結果可支持在該研究條件下，Socratic chatbot 可能有助於部分學生在特定批判思考測驗上的表現；其長期效果、不同學生群體的適用性與實際遷移能力仍需更多研究。

## 14. 與 AI 輔助思考相關的特殊檢查

當論點涉及 AI、推理模型或聊天機器人時，額外檢查：

- AI 的回答是否被當成獨立證據，而沒有驗證來源？
- 模型生成的理由是否只是語言上流暢，卻沒有可檢查依據？
- 使用者是否因 AI 表達確定而提高不當信心？
- AI 是否鼓勵提出反例、替代觀點與自我修正？
- 是否將較長的推理文字誤認為較好的推理？
- 問題是否缺少關鍵前提，導致模型產生冗長但無效的分析？
- AI 建議是否被直接轉成高風險決策？
- 是否清楚區分模型的推測、使用者提供的資料與已查證事實？

若問題本身缺少必要前提，先指出缺漏並提出澄清問題；不要用更多冗長推理掩蓋定義不完整。

## 15. 使用蘇格拉底式提問的問題庫

提問應服務於重建與驗證，不以連續追問取代實質分析。

### 澄清概念

- 這裡的「有效」「公平」「成功」具體指什麼？
- 這個主張適用於哪些人、時間或情境？
- 你是要描述現況、預測結果，還是提出行動建議？

### 檢查證據

- 哪項證據最直接支持這個主張？
- 這項資料能證明什麼，又不能證明什麼？
- 是否有相反資料或未納入的案例？
- 比較基準是什麼？

### 檢查前提

- 這個結論成立需要哪些條件？
- 哪個前提一旦不成立，結論就會改變？
- 這個前提目前是已知、推測，還是價值選擇？

### 尋找替代解釋

- 還有哪些因素可能造成相同結果？
- 如果沒有這個措施，結果是否仍可能發生？
- 是否存在另一個同樣能解釋資料的模型？

### 檢查決策

- 什麼證據會讓你改變判斷？
- 是否有較低成本、較可逆的下一步？
- 最壞情況是什麼？能否透過試辦或停損條件降低風險？

## 16. 最終品質清單

- [ ] 對 AI 生成內容已區分推測與查證資料。
- [ ] 高風險領域已明確標示專業查證需求。
