## Purpose

這支 skill 用在程式碼新建、重購或修改完成之後，依固定順序做七項檢查（冗餘未用、溢位邊界、例外錯誤、型別錯誤、邏輯錯誤、資安風險、執行效率），並直接修正找到的問題，交付修正後的程式碼與完整檢查紀錄。核心原則是「初步能執行不等於沒問題」，因此不以編譯或執行成功作為結束點，而是逐項往下查完七類風險後才收尾。

## Input

### Required（缺了就完全無法執行）

1. **目標程式碼本體**：可以是貼上的程式碼片段，或指定的檔案路徑。這是七項檢查唯一的作用對象，沒有這項無從開始。

沒有提供時，開口問：
「程式碼呢？貼上來或告訴我檔案路徑。」

### Optional（沒有也能跑，只是精確度或範圍會打折）

1. **程式語言／技術棧**：多數情況能從程式碼內容或副檔名自動判斷，語言曖昧不明時才需額外詢問。
2. **執行環境（作業系統、版本）**：影響修正建議的貼合度（例如 PowerShell 5.x 與 7.x 的 CP950、UTF-8-BOM 差異），缺少不影響七項檢查能否執行。
3. **專案框架／依賴套件清單**：有助於降低「冗餘未用」的誤判率（避免誤判動態載入、reflection），沒有時可退而標記為「疑似未用，待確認」。
4. **修正範圍限制**（例如只查資安、不查效能）：沒講就預設七項全查。
5. **是否允許直接修改檔案，或僅提供建議**：沒講採保守預設，先列出問題與修正方案，不逕自覆寫檔案。

## Workflow

### 步驟一：嘗試編譯或執行，確認初步通過

程式完成新建、重購或修改後，先嘗試編譯（或直接執行）。編譯無錯誤且能執行、或直接執行沒有一開始就報錯，算初步通過。此判準本身有已知盲點：初步通過不代表輸入資料後不會崩潰，也不代表輸出結果就是對的，只是排除最表層的錯誤，後續步驟仍要往下查。

### 步驟二：用測試資料實際執行，檢查結果

視情況決定測試策略：一般情況用隨機輸入即可；若本次改動涉及特定參數（例如新增了某個參數），則針對該參數的需求列出情境清單，逐項測試。用測試資料實際跑一次，檢查有沒有崩潰、結果對不對。

### 步驟三：依固定優先順序逐項檢查

先用 IDE 或編譯器的警告訊息找出冗餘未用的變數、函式、匯入（用工具查，不是人工讀碼找）。接著依固定順序檢查其餘六項，順序為：**溢位邊界＞例外＞型別＞邏輯＞資安＞效率**。

### 步驟四：溢位、例外、型別查核

**溢位邊界**：檢查字串長度、數字型別上下限，並且要特別檢查迴圈索引與陣列長度（這是容易被遺漏的部分，不能只做前兩項就視為完成）。

**例外處理**：發現例外崩潰時，優先追溯上游根本原因（治本），而非僅用 try-catch 包裹掩蓋（治標）。只有在追溯上游不可行時，才退而求其次先包裹。

**型別錯誤**：對照函式簽章、變數宣告與實際使用情境，系統化檢查型別是否一致，而非僅依賴執行時報錯才回頭處理。

### 步驟五：邏輯錯誤查核

先嘗試對照原本預期行為，重新讀一遍程式邏輯。如果程式碼長度、複雜度較低，或是熟悉的邏輯類型，優先用讀碼方式核對；如果讀不出來，才用測試資料的輸出結果反推問題所在。讀碼優先於結果反推，不可以只看輸出結果對不對就略過邏輯核對。

### 步驟六：資安風險查核

逐項檢查以下五類固定風險：輸入驗證、SQL injection、權限控管、API injection、密碼或金鑰是否直接寫在程式碼內（應改用環境變數）。每一類都要有明確的檢查結果，不可以籠統寫「已檢查資安」帶過。

### 步驟七：效率檢查與收尾迴歸測試

**效率**：對照程式碼是否有明顯冗長、可用更佳演算法替代之處，提出具體優化建議，而非僅標記主觀感受。

**收尾**：修正完成後，重新編譯執行一次，確認結果正確。此次迴歸測試僅針對本次改動（diff）範圍進行，非 diff 範圍可能存在修 A 壞 B 的風險，此風險目前沒有系統化機制防範，必須在交付時明確告知使用者。

## Output

依交付順序列出：

1. **編譯／執行結果紀錄**：初步通過與否，含錯誤訊息原文（如有）。
2. **測試資料執行紀錄**：使用的測試輸入與對應輸出結果。
3. **冗餘未用清單**：工具警告列出的未用變數、函式、匯入項目。
4. **溢位邊界檢查結果**：字串長度、數字上下限、迴圈索引、陣列長度的檢查結果。
5. **例外處理檢查結果**：例外情境與對應處理方式（治本或治標）。
6. **型別錯誤檢查結果**：型別不符項目與位置。
7. **邏輯錯誤檢查結果**：對照預期行為後的核對結果。
8. **資安風險檢查結果**：五類風險逐項檢查結果。
9. **效率優化建議**：可優化之處與建議演算法或寫法。
10. **修正後程式碼**：依上述九項檢查結果做出的實際修正。
11. **Diff 迴歸測試結果**：僅針對本次改動範圍重新編譯執行的確認結果。
12. **未覆蓋範圍聲明**：明確告知迴歸測試僅涵蓋 diff 範圍，非 diff 範圍的潛在副作用未測試。

## Checks

每一條都可用是或否回答，逐條核對後才能交付：

1. 程式是否已嘗試編譯或執行？
2. 編譯或執行過程中是否出現錯誤訊息，且已記錄？
3. 是否已用測試資料實際執行過一次？
4. 是否已用工具（而非純人工讀碼）找出冗餘未用的變數、函式、匯入？
5. 是否已檢查字串長度與數字型別上下限的溢位邊界？
6. 是否已檢查迴圈索引與陣列長度的溢位邊界？
7. 是否已對每個例外情境優先嘗試追溯上游根本原因，而非僅用包裹方式治標？
8. 是否已對照原本預期行為重新核對程式邏輯，而非僅憑輸出結果反推？
9. 是否已逐項檢查輸入驗證、SQL injection、權限控管、API injection、硬編碼密碼或金鑰這五類資安風險？
10. 是否已針對效率提出具體優化建議或替代演算法，而非僅標記主觀感受？
11. 修正後的程式碼是否已重新編譯或執行以確認結果正確？
12. 是否已明確標註本次迴歸測試僅涵蓋 diff 範圍、非 diff 範圍未測試？

## Rules

1. **嚴禁只做到「初步通過」就視為完成**：編譯成功或執行不報錯只代表排除最表層錯誤，不代表七項檢查已完成，不可以省略後續步驟就交付。
2. **嚴禁資安檢查籠統帶過**：五類資安風險（輸入驗證、SQL injection、權限控管、API injection、硬編碼密碼或金鑰）必須逐項列出檢查結果，不可以用「已檢查資安、無明顯問題」這類無法追溯依據的敘述取代逐項紀錄。
3. **嚴禁隱瞞迴歸測試範圍限制**：收尾測試僅涵蓋 diff 範圍，非 diff 範圍存在修 A 壞 B 的已知風險，交付時必須明確告知使用者此限制，不可以讓使用者誤以為全範圍都已驗證。
