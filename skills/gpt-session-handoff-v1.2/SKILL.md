# Session Handoff（session 交接摘要）

> **v1.2｜2026-07-16**：Skill 名稱改為 `gpt-session-handoff`，加入 ChatGPT Web 與 Codex 共用 metadata，並補上 Windows `PYTHONUTF8=1` 指引；補齊第〇節機器閘門（編號條目 ≧3、首條含錨詞「讀」＋「再回應」，錨定第一個編號條目、前導定位句合法）；誠實聲明「祈使語氣」為人工留意項不在閘門內；驗證流程的路徑與直譯器指令平台中立化（不再寫死 Linux 家目錄暫存路徑與單一直譯器名稱）。凍結標題與雜湊未動。
> **v1.1｜2026-07-15**：出處分級標籤平台中立化（【AI 建議未確認】，本 skill 可供任何 LLM 平台使用）；第〇節啟動指令新增 200 字上限機器閘門（編號祈使句、首條必為先讀完全文）；新增無程式執行環境的誠實降級。凍結標題與雜湊未動。
> **v1.0｜2026-07-15**：初版定版。九節交接骨架（含啟動指令節）凍結；交付形式定為對話內單一可複製 Markdown 區塊；驗證層為 validate_punct ＋ check_handoff 雙閘門。

這是一支**純文字型** skill：無重相依、無需安裝任何套件、離線可用。引擎是九節凍結骨架，內容是當前對話，兩者正交（房規四）。

## 目的

把當前 session 的核心脈絡、工作流、工作紀律、邊界、凍結契約、關鍵閘門、已確認的對話決議等，濃縮成一份**下一個 session 貼上就能接手**的交接文件。品質標準：新 session 讀完後，不需要回頭翻原對話，就能在正確的紀律與邊界內繼續工作，且不會誤踩已凍結的決定。

## 流程（五步，照順序走）

### 步驟一：對焦閘門（房規七，輕量版）

本 skill 的對焦負擔刻意壓到最低，照三欄決策表操課：

| 項目 | 歸類 | 規則 |
| --- | --- | --- |
| 交接範圍（整個對話／只交接某個子題） | 可推斷 | 對話只有單一主題就直接採用「整個對話」並在複述時講明；多主題混雜則必問要交接哪些 |
| 輸出語言 | 可推斷 | 照對話主要語言；台灣使用者一律正體中文＋台灣用詞 |
| 交付形式 | 預設值 | 對話內單一可複製 Markdown 區塊，不另存檔；使用者明講要檔案才存檔 |
| 骨架章節 | 預設值 | 九節凍結骨架，不增不減；不合用的節寫「本節無內容」而非刪節 |

只有「多主題混雜且範圍不明」時才停下來問一題；其餘情況一句話複述對焦結果後直接動工。

### 步驟二：全對話掃描

**由對話最開頭掃到最尾**，不准只看最近幾輪。逐輪標記四類素材：

1. **決議**：使用者明確同意、否決、修正過的事（含「你說得對，改成 X」這種轉折）。
2. **契約**：定版、凍結、版號、規格、不可再動的決定。
3. **紀律**：本 session 生效中的 skill、房規、使用者偏好（標點、用詞、格式、語言）。
4. **未決**：問了沒答、答了沒確認、明講「之後再說」的事。

掃描時同步做**出處分級**（作業紀律第五節）：分清哪些是使用者親口說的、哪些是 AI（執行本 skill 的助理）建議而使用者只是沒反對。後者不得寫成「已決議」，只能寫成「AI 曾建議，未獲明確確認」。這是本 skill 最容易造假的地方，列為最高風險區（作業紀律第三節）。

### 步驟三：填寫九節凍結骨架

照 `references/handoff-template.md` 的模板填寫。**九個章節標題的文字與順序為 v1.0 凍結契約，一字不可改、一節不可刪**（`scripts/check_handoff.py` 會用雜湊守門）。各節要領：

- **〇、啟動指令（給下一個 session）**：三條**機器閘門**：①內文上限 200 字（去空白計）；②至少三個編號條目（①～⑳ 圓圈數字或 `1.` 阿拉伯數字式）；③**第一個編號條目**須同時含錨詞「讀」與「再回應」（防搶答飄移；契約錨定編號條目，開場定位句屬合法前導）。祈使語氣為人工留意項，機器不驗（誠實聲明）。指示新 session：先完整讀本文件、載入第四節列出的 skill 與紀律、遵守第五第六節的邊界與契約、從第一節的「下一步」接手。
- **一、任務身分卡**：先答案（作業紀律第七節）：一句話講這個 session 在做什麼、進度到哪、下一步是什麼。新 session 十秒內能定位。
- **二、核心脈絡**：背景、目標、關鍵名詞與代號的定義。只放「不知道就會誤解後文」的內容。
- **三、工作流現況**：已完成／進行中／待辦三段，附檔案路徑、產出物名稱、版本號。
- **四、工作紀律與規範**：生效中的 skill 名稱、房規要點、使用者偏好（全形標點、禁破折號、正體中文等）。寫 skill 名稱讓新 session 自行載入，不要把整支 skill 內文抄進來。
- **五、邊界與禁區**：明講過不做、不碰、界外的事，含理由。
- **六、凍結契約與關鍵閘門**：已定版不可動的決定（逐條列，附定版時點），以及「動工前必須停下確認」的閘門。
- **七、已確認的對話決議**：逐條列，每條標示出處等級：【使用者明示】或【AI 建議未確認】。
- **八、未決事項與風險**：懸而未決的問題、已知地雷、新 session 最容易踩錯的兩三個地方。

長度原則：整份以「新 session 能接手」為準，寧可精準不要冗長；單節超過一頁就該再濃縮。

### 步驟四：驗證閘門（房規二，非 0 不交付）

把草稿寫進**當前環境的可寫工作目錄**（Linux／macOS 如 `~` 或工作資料夾，Windows 如 `%TEMP%` 或專案資料夾），再用**當前環境可用的 Python 直譯器**依序跑兩支驗證器（Linux 常為 `python3`，Windows 依 PEP 397 常為 `py` 或 `python`，以下以 `<python>` 代稱）。**任一退出碼非 0 就修到綠燈，不得請示放行**：

```bash
<python> scripts/validate_punct.py <草稿路徑>/handoff.md
<python> scripts/check_handoff.py <草稿路徑>/handoff.md
```

Windows 繁體中文環境提醒：驗證器讀寫一律 UTF-8，PowerShell 5.1 下請確保草稿以 UTF-8 存檔（勿用 CP950），必要時 `-Encoding utf8`。執行 Python 驗證器與測試前，設定 `$env:PYTHONUTF8 = "1"`，避免主控台使用 CP950 時發生 `UnicodeDecodeError` 或 `UnicodeEncodeError`。此設定僅適用 Windows；Linux／macOS 繼續使用環境中的 `python3`。

- `validate_punct.py`：全形標點＋禁破折號（共用正本，房規三）。
- `check_handoff.py`：九節標題齊全、順序正確、標題雜湊未被動過、無空節、無殘留佔位符（TODO／FIXME／待填）、第〇節三條閘門（200 字上限、編號條目 ≧3、首條含錨詞）。

### 步驟五：交付與滿意度迴圈

驗證全綠後，把整份文件放進**單一 fenced code block**（語言標記 `markdown`）貼在對話內，讓使用者一鍵整塊複製。若文件內部含有三反引號的程式碼區塊，外層改用**四個反引號**包覆以免巢狀斷裂。交付後必問是否滿意；不滿意就依方向修改、**重跑步驟四**再交付，重做不限次數。

## 能力邊界（先講清楚，別硬做）

- **無程式執行環境的降級**：本 skill 可供任何 LLM 平台使用；若當下環境跑不了 Python 驗證器，降級為「照凍結模板逐節自檢＋人工核對標點」，並在交付時明講「本次未跑機器驗證」，不得假裝驗過（誠實降級）。

- **上下文截斷誠實聲明**：交接品質受限於當下可見的對話內容。若對話早段已被截斷或壓縮，只能交接還看得到的部分，並在第八節明寫「早段脈絡不可考，建議向使用者確認」；**絕不編造沒看到的脈絡**。
- **不替使用者做新決定**：摘要只轉述已發生的事。掃描時發現矛盾（例如前後兩次決議打架），寫進第八節請新 session 向使用者釐清，不自行裁決。
- **不跨對話**：本 skill 只交接「當前這一個對話」。要彙整多個歷史對話，需明確告知使用者那是另一回事，並經同意後才動用對話搜尋工具。
- **驗證器涵蓋誠實聲明**：`check_handoff.py` 只能驗結構完整性，驗不了內容正確性；內容正確性靠步驟二的出處分級與交付前自我攻擊（作業紀律第六節）把關。

## 版本與凍結

- 九節標題文字與順序為 v1.0 凍結契約，帳本見 `FROZEN.md`，程式級守門在 `scripts/check_handoff.py`（雜湊比對，snippets 第 11 段範式）。
- 要改章節結構一律另開新版（major），舊骨架原封保留，不就地修改。
- 回歸測試 `tests/test_handoff.py`：凍結雜湊斷言、驗證器乾淨過髒的擋、空節擋、佔位符擋。改動本包任何腳本後必跑，全 PASS 才算沒踩契約。
