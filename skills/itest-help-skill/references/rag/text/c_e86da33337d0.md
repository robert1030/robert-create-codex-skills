# Test Case Editor > Quality Center page on the Test Case Editor > Setting preferences for the Test Case Editor > Properties in: Spirent > Editors > Test Case Editor > EXEC Steps

- **Automatically add 'then' and 'else' clauses on new 'if' steps**：Auto-populate the full structure of new if steps with hints that help you to create a working loop. Default: checked
- **Automatically add nested placeholder steps inside container steps (if, while, for, foreach)**：When you add a flow control step, iTest can auto-populate steps that act as placeholders for the steps you will eventually add. Notice that the steps are indented under the container step to indicate that they are a part of the loop construct. Skipping, moving, or otherwise editing the container step affects all steps in the loop. Default: checked
- **Display warnings in the Step Issues view for analysis rules that cannot be evaluated at design time**：When an analysis rule includes a field replacement whose value can be determined only after particular steps in the test case execute, then, while you are editing the test case, iTest cannot guarantee that the field replacement will operate successfully. Check the box to generate warnings in these cases. Default: checked
- **Display a warning when the user adds a got step or goto action is added**：This option applies to imported Spirent SVT steps only. When you add a goto step or action, iTest displays a warning to notify you that the goto action is deprecated (no longer an active part of iTest). The warning appears both as icon in the left column of the Test Case editor’s Steps page and an entry in the Step Issues view. The warning reminds you that adding goto steps is poor practice for software development. Uncheck the box to disable such warnings. Default: checked
- **Display the full URIs for foreign procedure calls**：Default: unchecked While editing a call step or CallProcedure step that calls a foreign procedure, iTest displays the URI of the test case (procedure library) that contains the procedure definition. This helps you to identify the correct procedure library so that you can select the correct procedure and then finish defining the calling step. If this option is unchecked (default), then, after you finish editing the command in the Description cell (adding the procedure name and any arguments) and exit the cell, the full URI to the procedure library will no longer appear — only the procedure name plus arguments remain. This makes it easier to read and understand the step. If you check the box, then the full URI to the procedure library (test case) remains on display in the Description cell.
- **Display a warning when inserting call steps with missing required arguments**：While editing the arguments for a call step or CallProcedure step (either in the Description cell or while using the Procedure Call wizard), it is possible to define a call that does not include all required arguments. Check the box to display a warning in this case. Default: checked
